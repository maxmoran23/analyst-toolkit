# Reference data — transaction monitoring

A small, committed sample of the synthetic input this framework's engine consumes.
It holds 120 customers and 800 alerts versus the 5,000 / 50,000 used for validation (1.6%). The full validation population is regenerated from seed into `data/`
(gitignored by design — credibility is reproduction-from-seed, not data-in-repo);
this pack exists so the framework folder is fully self-contained for a reader
browsing it on its own.

> **In plain terms:** Two small spreadsheets — made-up customer profiles and the monitoring alerts raised
> on them, labelled with the right answer — so you can see what the triage engine
> reads before the full 50,000-alert validation.

## `customers.csv` — 120 rows (validation scale: 5,000)

Synthetic customer profiles with expected-activity baselines.

| Column | Meaning |
|---|---|
| `customer_id` | Unique customer identifier. |
| `segment` | Customer segment (retail / SMB / corporate ...). |
| `risk_rating` | Customer risk rating. |
| `expected_amount` | Expected monthly activity value (documented baseline). |
| `expected_count` | Expected monthly transaction count. |
| `home_country` | Home country (fictional assignment). |
| `business_type` | Documented business type (explains some alert patterns). |

## `alerts.csv` — 800 rows (validation scale: 50,000)

Monitoring alerts — each a window of aggregated transaction features for one customer.

| Column | Meaning |
|---|---|
| `alert_id` | Unique alert identifier. |
| `customer_id` | Alerted customer (joins to `customers.csv`). |
| `window_days` | Length of the aggregation window in days. |
| `total_in` | Total inbound value in the window. |
| `total_out` | Total outbound value in the window. |
| `txn_count` | Transaction count in the window. |
| `near_threshold_count` | Transactions just below a reporting threshold (structuring signal). |
| `distinct_in_cp` | Distinct inbound counterparties (funnel signal). |
| `distinct_out_cp` | Distinct outbound counterparties. |
| `passthrough_ratio` | Outbound / inbound ratio in the window (pass-through signal). |
| `same_day` | Same-day in-and-out indicator. |
| `high_risk_geo_fraction` | Fraction of value touching high-risk geographies. |
| `label` | Ground truth: 1 = genuinely suspicious; 0 = false positive. |
| `category` | Construction category — named false-positive reason (within_profile, below_typology, documented_context, ambiguous_residual) or true-suspicious flavour (clear_typology, emerging). |

## Regeneration

From the repository root:

```bash
python3 _tooling/build_reference_data.py --only transaction-monitoring
```

The build is deterministic (seed 42): every run reproduces these files
byte-identically, and the `reference-data` CI job re-derives and diffs them on
every change, so this pack can never silently drift from the generator.

All records are seeded synthetic data produced by this framework's own
`generate_synthetic_data.py`. No real person, entity, account, or event is
represented; any resemblance to a real name is coincidental by construction.

**Confidence: HIGH — generated by the same seeded generator as the validation population and byte-verified by the `reference-data` CI job on every change.**
